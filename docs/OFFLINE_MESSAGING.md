# Аварийная доставка сообщений

Цель: `Маяк` должен доставлять сообщения не только через центральный сервер, но и через любые доступные каналы связи.

## Базовая идея

Сообщение превращается в зашифрованный конверт:

1. клиент создаёт полезную нагрузку: отправитель, получатель, текст, время, id сообщения;
2. клиент шифрует её ключом комнаты или публичным ключом получателя;
3. наружу выходит пакет, который можно передавать через интернет, локальную сеть, Bluetooth, Wi‑Fi Direct, QR, файл или другое устройство;
4. посредник не читает содержимое, а только переносит пакет;
5. получатель расшифровывает пакет и добавляет сообщение в историю.

В `localhost`-прототипе уже есть демо этой единицы: `Аварийная доставка → Офлайн-пакет`.

## Режимы работы

### 1. Online

Обычный серверный режим:

- WebSocket/HTTP API;
- очередь сообщений;
- push-уведомления;
- синхронизация между устройствами;
- сервер хранит только зашифрованные конверты.

### 2. Плохой интернет

Клиент всегда принимает ввод пользователя:

- сообщение сразу появляется в чате как `ожидает отправки`;
- пакет попадает в локальную очередь;
- при появлении сети клиент отправляет очередь;
- повторная отправка безопасна, потому что у каждого сообщения стабильный id.

### 3. Локальная сеть

Если интернет отключён, но Wi‑Fi-роутер или точка доступа живы:

- один клиент создаёт локальную комнату;
- другие подключаются по QR/кодовой фразе;
- пакеты ходят внутри LAN;
- после восстановления интернета история догоняется через сервер.

### 4. Nearby/offline

Нативные клиенты получают транспортный слой:

- Android: Nearby Connections или Wi‑Fi Direct;
- iOS/macOS: MultipeerConnectivity;
- кроссплатформенный мост: через общую Wi‑Fi-сеть, локальный hotspot или relay-устройство.

Этот слой не должен знать формат чата. Его задача — передать бинарный пакет.

### 5. Store-and-forward

Устройство может быть “почтальоном”:

- принимает чужие зашифрованные пакеты;
- хранит ограниченное время;
- передаёт дальше, когда встречает получателя или другой узел;
- не имеет ключей для чтения содержимого.

## Что важно для безопасности

- Не притворяться чужими белыми сервисами и не строить продукт на маскировке.
- Не хранить plaintext на сервере.
- Не считать демо с общим паролем финальной криптографией.
- Для реального продукта перейти на ключи устройств: X25519/Ed25519, double ratchet или проверенную библиотеку протокола.
- Делать понятную проверку контактов: QR, safety number, короткий код сверки.
- Хранить локальную базу зашифрованной.

## Первый MVP

1. Локальная очередь сообщений.
2. Экспорт/импорт зашифрованного пакета.
3. LAN-комната через WebSocket-сервер на ноутбуке или телефоне.
4. Android Nearby prototype.
5. iOS Multipeer prototype.
6. Единый формат пакета для всех транспортов.
